# 需求规范标准 v2.0

## 1. 需求完整性检查清单

一个完整的需求应包含以下要素：

### 1.1 基本信息
- [ ] 需求单号（如 REQ-2026-XXX）
- [ ] 标题（简洁描述需求目标）
- [ ] 优先级（critical / high / medium / low）
- [ ] 提交人与提交日期

### 1.2 业务描述
- [ ] 背景与动机（为什么要做）
- [ ] 目标用户与场景
- [ ] 预期效果

### 1.3 约束条件
- [ ] 功能性约束（必须/至少/不得/不能）
- [ ] 非功能性约束（性能、安全、合规）
- [ ] 外部依赖（第三方服务、数据源）

### 1.4 实体定义
- [ ] 涉及的核心业务实体
- [ ] 实体间关系
- [ ] 字段与类型

### 1.5 验收标准
- [ ] 正向场景（happy path）
- [ ] 异常场景（错误处理）
- [ ] 边界条件

## 2. 需求评审标准

| 维度 | 权重 | 说明 |
|------|------|------|
| 完整性 | 30% | 上述 checklist 覆盖度 |
| 清晰性 | 25% | 无歧义，可量化 |
| 可行性 | 20% | 技术可实现 |
| 一致性 | 15% | 与已有系统不冲突 |
| 可测试性 | 10% | 验收标准可执行 |

## 3. 常见需求缺陷

1. **缺少异常场景**：只描述 happy path
2. **约束模糊**："尽量快" — 应量化为具体指标
3. **实体未定义**：直接使用业务术语但未说明
4. **缺少验收标准**：无法判断是否完成
5. **忽视安全合规**：涉及用户数据但未提隐私要求

## 4. 报告模板

分析报告应包含：
- 需求概述
- 完整性评分（按维度）
- 缺失项清单
- 改进建议
- 风险提示
